## What each PR does

**#16, P1-J** (plan: `docs/plans/sprint-1-p1j-password-hash.md`).

- `jantrik_app` can no longer read `users.password_hash`: SELECT is granted column by column,
  except that one.
- The login lookup it could run returned any user's hash by phone. That was the bigger hole, and it
  is closed too.
- Password login now uses a new database login, `jantrik_login_app` (`DATABASE_LOGIN_URL`). It can
  run exactly one function, the hash lookup; the API verifies with argon2 as before.
- Tests pin which columns and functions each login can reach, so a later change cannot reopen
  this.
- **Before you merge it, on this PC:**
  1. create the role (the command is in the PR body and in `docs/database.md` → Database roles);
  2. add `DATABASE_LOGIN_URL` to `.env` (`.env.example` has the line);
  3. then `pnpm db:migrate`.
  - The migration stops with a clear message if the role is missing.
  - On a server, the order is in `docs/deploy.md` → Upgrades.

**#18, P2** (plan: `docs/plans/sprint-1-p2-files.md`).

- **Settings → Institute profile:** names, EIIN, address, contact and head of institute; logo,
  signature and seal (OWNER/ADMIN).
- **Student photos:** upload and replace on the student page, and the photo on the report card,
  for staff and guardians.
- **Storage:** files live in Postgres behind a `FileStore` interface, under RLS. Every upload is
  re-encoded by `sharp` and the uploaded bytes are never stored.
- **Caps:** per kind (photo 200 KB, logo, signature and seal 100 KB) and per institute (1 GB,
  `FILE_STORAGE_PER_TENANT_MB`).
- **Uploads:**
  - the browser shrinks the image first;
  - uploads hold no database connection while the body arrives;
  - at most 2 uploads in flight per person and 16 per server.

## Reviews

A review subagent read every PR that touches security, auth or the database. Its findings were
fixed on the PR, each with a test that failed first where one could.

- **#16, two rounds.**
  - Round 1: hiding the column alone left a batched password oracle (any user, about 200,000
    guesses in one query), which led to the dedicated login.
  - Round 2: the migration could half-apply if the role was missing; it now checks first and can
    run again.
- **#18, three rounds.**
  - Round 1: uploads ran inside the 15 s request transaction (slow phones failed every time, and 10
    slow uploads could take every institute's connections).
  - Round 2: upload bodies had no limit in memory; authorization could go stale during a long
    upload.
  - Round 3: an upload slot could leak when the phone disconnected early.
- **#17, one round:** the test-phone counter would have wrapped on 29 November, invisible
  characters slipped past the name rule, and an origin with a login part was reduced to another
  host. The fixes only refuse more, so there was no second round.
