## Task 3: Deployment readiness (PR #8)

**Done** (no accounts, no servers, placeholders only):

- **Docker images** for the API (also the receiver and the queue worker, by command), the web app
  (standalone output only inside the image, so `next start` and CI are unchanged) and a
  `migrate` image.
- **Production compose example** (`deploy/`):
  - Postgres 16 and Redis (AOF, `everysec`, `noeviction`, a password), neither published to the
    host;
  - a one-shot `migrate` service, the only one with the owner's credentials; it applies the
    migrations and loads the templates, and every other service waits for it to succeed;
  - the API, the web app, the receiver (port 4080, plain HTTP for the devices, with only its own
    variables) and a separate queue worker (the API's own workers switched off there; by default
    the API still runs them, as before);
  - Caddy for HTTPS with app / api / device / platform host routing, and a stopgap rule that
    refuses `/platform/*` from foreign origins.
- **Database roles:** `deploy/postgres/create-roles.sh` creates every role the migrations need,
  for production only (no dev or test databases), safe to run again; documented for a managed
  Postgres too.
- **Production env checks** for the API, the worker and the receiver:
  - they refuse the dev SMS providers, `TRUST_PROXY=true`, http or localhost CORS origins, example
    or short secrets, an owner or superuser database login and missing required variables;
  - the receiver refuses the API's secrets;
  - tests still run as `NODE_ENV=test`, with no flag that relaxes production.
- **`SMS_PROVIDER=none`** for a server without an SMS gateway: every send fails with "no SMS
  gateway is configured", so nothing is sent. Until a gateway is chosen nobody in an institute
  can sign in (OTP is the only way; no production path sets a password); platform admins can.
- **Backups:** backup and restore scripts (custom-format dump, checksum, retention, an upload hook
  left as a placeholder); restore refuses a non-empty or protected target. A restore check
  compares migrations, tables, functions, policies, owners and row counts, and tests that RLS
  still hides students without a tenant. It runs in a new CI job, "Production roles, backup and
  restore".
- **`docs/deploy.md`:** a beginner's runbook (server sizes, DNS for the four subdomains, HTTPS,
  firewall, roles → migrate → start, the first platform admin through the CLI, upgrades,
  monitoring, backups and a restore drill, a checklist), provider-neutral.

**Verified locally:** the images built; the whole stack ran once under a separate project name
(all healthy, `/health` 200, the receiver answered 403 to an unknown serial, five queue workers,
none in the API, Redis settings confirmed, a backup and a restore drill inside the stack), then
