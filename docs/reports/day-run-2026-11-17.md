## Task 1, P1-J8: done ([#20](https://github.com/omerFixesBugs/jantrik-school/pull/20))

**The problem:** an SQL injection in an ordinary request could set `app.user_id` / `app.tenant_id`
with `set_config` and then act as anyone: write another person's `password_hash`, insert a session
for them, change their phone, or make itself OWNER of any institute. On `integration/sprint-1`, 6
of the 7 attacks in the new `account-takeover.test.ts` worked.

**The option chosen (P1-J8a):** a **signed request context**. Narrower write rules (only the
password and sessions behind special functions) would still let an injection make itself OWNER of
another institute; the signed context closes impersonation as a whole.

- The API signs the institute, the person, the connection's backend and the transaction start with
  HMAC-SHA256. The key is generated by the migration inside the database; only
  `jantrik_login_app` (#16's login) and the schema owner can read it (P1-J8b).
- `app_current_tenant_id()` / `app_current_user_id()` believe only a valid signature for this exact
  transaction; anything else raises an error (P1-J8c, P1-J8d). `app.tenant_id` / `app.user_id` mean
  nothing any more.
- Every policy now calls them as `(SELECT …)`, checked once per statement; a test fails on any bare
  call in policies, functions, views, defaults and CHECKs (P1-J8e).
- **No new role and no new `.env` line.** It needs #16's `DATABASE_LOGIN_URL`, which the API and the
  worker now also use to load the key. Production refuses to start without the key (P1-J8h).

**Reviews, two rounds, every finding fixed with a test:**

- **Round 1** (no must-fix): temporary objects left on a pooled connection could hijack the next
  request in development and CI (production already revoked them) → the migration now revokes
  `TEMPORARY` from `PUBLIC` on its database and the start-up check refuses it in production
  (P1-J8i). The time between `migrate` and the restart cached empty roles in Redis for 5 minutes →
  the upgrade now stops the API and worker first, and the cache keys have a new generation
  (P1-J8j). Smaller: the import job's identity, the key's pads, a wider guard (P1-J8k, l).
- **Round 2** (one must-fix): an injection in one of the three queries that ran outside a
  transaction could leave a transaction with a held cursor open on a pooled connection, which the
  next request would then sign (a cross-institute read, reproduced). None of the three was
  injectable, but the guarantee was broken → the pool now closes any connection returned with a
  transaction open, signing refuses a transaction that is not fresh, and the three queries run in
  transactions (P1-J8o). Also: a login's stored role settings (`ALTER ROLE … SET`) are refused in
  production (P1-J8p); only the uploader may start an import (P1-J8q).
- I ran the round-2 reviewer's attack script against the fixed branch myself: no leak.

**Cost:** about 38 µs per check, once per statement. A simple count went from 6.0–6.4 ms to 7.4–8.1
ms (one more round trip); ten statements 25.9–26.1 → 26.7–27.9 ms. **One slowdown to know
(P1-J8n, your decision):** the planner no longer sees which institute a query is for, so on a very
large institute the student list went from about 1 ms to 6 ms. Passing the institute explicitly in
the paged lists brings the old plan back; recommended as a small follow-up PR.

**Not changed, recorded:** the platform login's context (P1-J6, as before); a login can still change
its own password (PostgreSQL allows it, P1-J8m); RLS separates institutes, not roles inside one, so
an injection can still write rows in its own institute (P1-J10, follow-up with options).

**For you before merging #20:** nothing beyond #16's setup. Upgrade order: stop the API and the
worker, `pnpm db:migrate`, start them (docs/deploy.md → Upgrades). The migration also revokes
`TEMPORARY` from `PUBLIC` on the database it runs on.

    codes; SMS queued at 20:59 went out after 21:00.

    confirmed, and the page showed the old cost; a quiet-hours wait could hide lateness.
- **Defaults to confirm (P6-b16, P6-b17):** at send time, a scheduled broadcast that would cost
  more than 10 % (and more than one SMS) above the confirmed cost is not sent (status
